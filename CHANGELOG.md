# Changelog

All notable changes to this project are documented here.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Remote servers
Visor manages supervisord on your Linux servers over SSH, each in a tab beside this computer's, like a browser. Nothing is installed on the server.
- **Remote servers** has its own page, in the sidebar above Doctor and Settings: every server with its connection (Connected, Reconnecting…, Can't connect, Not open), Add a server, and how many may be connected at once. The + beside the tabs opens a saved server that isn't open; with none, it points to that page. While a server is connecting, its button reads Connecting… and can't be pressed again (nor its entry under +).
- **Add a server** on the Remote servers page: name, tag, colour, host and port (or a Host alias from `~/.ssh/config`, whose user, port, key and ProxyJump are used), user, password and/or SSH key (empty uses `~/.ssh/config` and your SSH agent), **Use sudo** with its own password (or the SSH one, or none for NOPASSWD), **Read only**, and under Advanced the config path, a jump host and which outside changes notify you. Passwords stay in your Keychain or keyring; `servers.json` holds none.
- **Test** connects with the form as it is and shows what this user can do there: the SSH login and host key, sudo, supervisord.conf, the socket (forwarded over SSH, through sudo, or why not, with its owner and mode), how many configs it can read, and supervisord's version. Each gap comes with its fix (turn on Use sudo, or let the user in through a group, with the commands to copy). A server that can't connect opens no tab: **Connect** saves the server and, when it can't connect, keeps the form open with the report saying why (a wrong password, a key that needs its passphrase, a host that doesn't answer). **Connect without saving** opens a tab that keeps nothing (secrets in memory only) and is forgotten when it closes. Editing a server whose tab is open reconnects it (Reconnect).
- A login refused for the user you typed says so ("The server refused the login for …"), even when the key file is locked: the passphrase is only blamed when your SSH agent doesn't hold that key.
- **Host keys**: a server Visor hasn't seen shows its key's fingerprint to check before you trust it, in Visor's own list; `~/.ssh/known_hosts` is read, never changed. A changed key is refused, with the command that removes the old one.
- **sudo is asked once per connection**, not on every check: Visor runs a small Python helper for the length of the connection (Python comes with supervisord). A refused password is never tried again on its own, so it can't lock the account.
- **Tabs**: this computer's tab is first and always open; servers open in the order you open them (3 at once by default, set on the Remote servers page). Each tab keeps its page. Ctrl+Tab and Ctrl+Shift+Tab move between tabs; ⌘W (Ctrl+W) closes a server's tab. Visor starts with only this computer's tab.
- A server tab has everything the dashboard has (processes, groups, actions, logs, Issues, notifications, the supervisord log) except changing configs: configs on servers are **read only** in this version, with **Download a copy** in place of Reveal in Finder. The banners say so in words, with no Doctor link: editing configs on servers, through sudo too, comes in the next version. The explanation finds a program such as `php` on the server's own PATH (the one systemd gives supervisord).
- **Production** servers ask before Stop, Restart, Signal, Clear logs, Stop all, Restart all and restarting or shutting down supervisord, naming the server. **Read only** servers show no actions.
- The menu-bar popover has a section per open server (its state, its processes, Restart all on it, Open tab); with servers open, this computer folds the same way, every section starts folded, and the header says "This Mac and 2 servers". The icon shows the worst state across tabs. Notifications name the server and open its tab.
- A server's report (Server report in its sidebar) is laid out as Doctor is: the lens with a segment per check, each check's status in words, and the fix under it.
- When a server's SSH connection drops, its tab says **Reconnecting…** and comes back on its own (2 s, then longer, up to a minute). While it can't, an issue says "Can't reach the server over SSH", apart from "supervisord isn't responding".
- When supervisord's socket is closed to your user (a Linux package's, owned by root), the issue and notification say "this user isn't allowed to open its socket (permission denied)" instead of Go's dial error.
- On a server, the group fix says to add that user to the group and check again: each connection is a new SSH login, so nobody needs to log out. A tab that can't reach supervisord says why, as this computer's does (Not answering, Not running, Not connected); **No access** is kept for a refused login or host key.
- On a server's tab, the breadcrumb names the server instead of "Local", and Stop all / Restart all ask "… on <server>?".
- A live log opens at the start of a line, not partway through one.
- A crash leaves its trace in `crash.log` in the state folder (an app opened from Finder or the dock has no terminal to print it to).

### Activity
- A new **Activity** page on every tab: processes started, stopped or restarted, programs added or removed, config files changed on disk, supervisord restarted or down, each marked **By Visor** or **Outside Visor** (supervisorctl, a deploy script, another person), by day, with filters. The dashboard shows the latest change made outside Visor in a strip.
- Changes made outside Visor **notify you**, grouped ("3 processes restarted outside Visor on cpcsl dev"); mute each kind in Settings (this computer) or a server's Notifications.
- A process that is slow to stop (Laravel Horizon waits for its jobs) and is already starting again at the next check counts as restarted.
- A config file edited after supervisord restarted shows as changed on disk (in Activity and the changes banner), instead of "Visor can't tell if it changed".
- When supervisord is down, Issues → supervisord log shows the end of its log file (on a server, read through the connection), which often says why; the down banner links to it.

### A new look
Every screen was redrawn on one set of colours, buttons and type, in light and dark. Buttons still do what they did; the few flow changes are noted below.
- A new app icon, Pulse: a bright ring on dark glass with a mint pulse line. The menu-bar icon is the same ring and pulse, with a hollow badge for a warning and a filled one for an error.
- The dashboard opens with a health strip: one sentence ("2 processes are failing", "All 12 processes are running"), the names of what fails with **Show them**, and small counts, in place of the six tiles. Failing processes come first within their config, on a tinted row with the full reason. Shutting supervisord down now points to Doctor.
- When supervisord isn't running (or wants a password, or won't let Visor in), the dashboard says so in one plain line with **Open Doctor** and **Try again**; the raw error is under Show details. The counts show dashes, the actions that need supervisord are off and say why, and your configs stay listed. When supervisord is there but doesn't answer a check (it timed out, or sent an HTTP error), it says "supervisord isn't answering" and that Visor keeps checking. The sidebar says "Not running" only when supervisord isn't running, "Not answering" for that, and "Not connected" for any other connection problem. A notification for a turned-down password says so ("supervisord wants a password") instead of "Visor can't reach it".
- A config's page has a clearer header (breadcrumb, title, a failing badge, the Watching switch) and a full-height Logs tab with a live dot. Overview opens on "Only problems" when the file has any.
- Issues has one summary line instead of tiles, each kind as an icon and a word, and the whole of what happened with its process and config under it. A crash loop is red there, as it is in the bell and the banners.
- The notification panel (the bell) groups notifications into Today and Earlier, with the severity icon before each title and unread ones in bold.
- macOS banners start with a coloured severity icon (red, orange or blue) before the title, have a one-sentence body that starts with the config file, and stack by config file.
- The menu-bar popover lists failing processes first, in a "Needs attention" group (named `group:name` when the two differ, so two failing `worker`s can be told apart), then each config with its Watch switch; rows show only the actions that apply. When supervisord isn't running it says so plainly, and **Open Doctor** takes the main window straight to Doctor.
- The menu-bar popover was redrawn: each row shows the name over its state and time ("Running · up 4s", "Fatal · failing 3m"), with Start, Stop and Restart as words. Several copies of one program are one row, "mailer-worker ×2", that says how many run ("3 of 4 running · 1 failing", in red when one fails) and unfolds to show each copy; its buttons act on every copy. A failing copy is still listed under Needs attention too. Each config's name is a small heading with a bell beside it to watch the file or not, and the footer is one row: Restart all, Apply changes and Open Visor….
- Add new: Write it lists what to fix before saving, each linked to its line, and a save bar stays at the bottom with the status and a Save that says why it waits ("Fix line 4 to save"). The form has its titles inside the cards, a checked template chip and a preview that counts what to check. A config's editor uses the same save bar.
- **Copy an existing config**: Add new → Copy an existing config… opens a copy of any config under new names (`<name>-copy`, then `-copy-2`…), lists what it renamed and warns about values that still name the original and about any log file the copy would share with it (a fixed path, not `AUTO` or one with `%(program_name)s`). The copy's file name stays inside the include pattern (`web-svc.ini` → `web-copy-svc.ini` for `*-svc.ini`). Nothing is written until you save.
- Settings starts with General. Polling, crash loops and issue history share one "Checking and history" card, every row has its label on the left and the control on the right, and Appearance (System, Light, Dark) is only in Settings now, no longer in the sidebar.
- Doctor uses the app's look: a status word beside every check and the fix in one card under the checks.
- "What this config does" is now one card per program instead of one long paragraph. Each card shows the program's name, whether it is running (or "2 of 4 running", or what is failing), what it does in one short sentence, and why it can't run when supervisord says so. Click a card to see its lines; failing programs start open, the others closed, and Expand all / Collapse all open or close them together. The Config tab and Add new use the same cards, with each line written above what it means and the setting's name picked out from its value. "Only problems" never hides a failing program. A Laravel command Visor doesn't know reads as "the Laravel command ocpp:watch-ceilings" instead of "a PHP script".

### Linux (in progress, for the first beta)
Visor is coming to Linux desktops (Ubuntu 24.04+ and Fedora 40+, GNOME and KDE, x86_64).
- CI runs vet, lint, the Go tests with a real supervisord and a native GTK 4 / WebKitGTK 6.0 build on Ubuntu 24.04, beside the macOS job. To save Actions minutes (a macOS minute counts ten times in a private repo), pull requests run the two Linux jobs; the macOS job runs on `main`, by hand (Actions → CI → Run workflow) and on a PR labelled `macos`. A push that changes only docs runs no CI.
- The Windows scaffold Wails generated (`build/windows/`, its tasks and the `.ico`) is gone: Visor has no Windows build.
- Words follow the OS: on Linux Visor says Ctrl+N (not ⌘N), "Show in file manager" (not Reveal in Finder), "Saved in your keyring", "tray" for the menu bar, and leaves out the macOS-only System Settings links and rows. Go's new `SystemService.Platform` is the one source (`platform.Current`, `platform.Describe`); `frontend/src/lib/platform.ts` loads it before the app mounts. The server build takes `VISOR_PLATFORM=darwin|linux`, so the UI tests check both: the shared e2e Visor words things as on Linux and `platform.spec.ts` starts a macOS one beside it.
- Keyboard shortcuts come from one table (`lib/shortcuts.ts`). Linux has no app menu bar (Wails would draw it inside every window, the popover too), so the main window carries out Ctrl+, Ctrl+N, Ctrl+1, Ctrl+2, Ctrl+F, Ctrl+R, Ctrl+W and Ctrl+Q itself; Ctrl+C stays copy. Find in a log now goes through the same Find choice as the menu bar's.
- Launch at login on Linux: an XDG autostart entry, `~/.config/autostart/dev.getvisor.visor.desktop` (or under `$XDG_CONFIG_HOME`), written whole through a temp file, with `Exec="<Visor>" --login`. An AppImage is started from its own file (`$APPIMAGE`), never from its temporary mount, and launch at login stays off while it sits in `/tmp` or can't run. An entry left by another copy reads as off. `platform.XDGAutostart`, `platform.Executable`.
- One Visor per user on Linux too: an installed copy (`platform.Installed`: the AppImage, or a binary in `/usr/bin`, `/usr/local/bin`, `/opt` or `~/.local/bin`) hands a second launch over to the running one; dev builds still run beside it. The GTK application id is `dev.getvisor.visor`, and closing the last window keeps Visor in the tray instead of quitting.
- Files on Linux: Show in file manager selects the file through the file manager's D-Bus interface (Nautilus, Dolphin…), or opens its folder with `xdg-open`; Open uses `xdg-open` but only shows desktop entries, AppImages and packages; a log always opens in the default text editor (`gio launch`), whatever its name, and is shown instead when no text editor is set. Commands found on the login shell's PATH, then `/usr/local/bin`, `/usr/bin`, `/bin` and Homebrew on Linux.
- The tray menu's "Launch at login" check mark and "Notifications (N)" now follow changes on Linux (the menu was being rebuilt as a GTK menu, which cut it off from the tray, so the count could lag behind the bell).
- Saved passwords on Linux go to the keyring (the Secret Service: GNOME Keyring or KWallet), and messages say "keyring" there. When no keyring answers (none running, or a session without one), saving says "No keyring is running (GNOME Keyring or KWallet), so the password can't be saved. Visor uses it until you quit", the connection keeps the password until Visor quits, and Settings shows "Kept until Visor quits: no keyring is running". `settings.SessionFallback`, `SettingsView.PasswordThisSession`.
- Notifications on Linux, through the desktop's notification server (GNOME Shell, Plasma): the same severity icon, title and one-sentence body as on macOS, with the body's `&`, `<` and `>` escaped (those servers read it as markup), and a click opens Visor on Issues. Settings says "Allowed" when a server answers; without one the test notification says no desktop notification service is running.
- The Linux tray icon is the Pulse lens in colour (it reads on GNOME's dark bar and on light panels), with the unread count drawn in a badge in the health colour (1–9, then 9+), or a dot for a warning or an error. "Show the unread count on the tray icon" turns the count off. Its tooltip says "Visor". `trayicon.Coloured`, with reviewed images in `internal/trayicon/testdata`.
- The popover on Linux: the tray menu starts with **Show status…** (GNOME's panel opens the menu on a click and never tells Visor), the popover stays open when it loses focus (on Wayland it never gets it) and has a close button, and Esc or Show status… again close it. On Wayland the desktop decides where it opens.
- On Linux the window follows the appearance too: GTK's dark preference (title bar included) follows Settings, and System follows the desktop's dark setting live through the settings portal.
- Doctor on Linux: it looks for `/etc/supervisor/supervisord.conf` (Debian, Ubuntu) and `/etc/supervisord.conf` (Fedora) first, and Homebrew's only on macOS. It reads the distro from `/etc/os-release` and shows its commands: `sudo apt install supervisor` (or `dnf`, or `pacman`), and for the system's supervisord `sudo systemctl enable --now supervisor` (`supervisord` on Fedora and Arch) to copy, never run; a config of your own still has Start supervisord. A socket root keeps gets the group fix, step by step: let a group use the socket (`chmod=0770`, `chown=root:supervisor` under `[unix_http_server]`), join the group, restart supervisord, log in again. When the config already names a group you aren't in, or you joined but haven't logged in again, it says only that. A config folder root owns gets `sudo chgrp supervisor <dir> && sudo chmod g+w <dir>`. It warns when the desktop has no tray (with the GNOME AppIndicator package) and when the AppImage runs from `/tmp`. "Your computer is ready". New `doctor.PackagesFor`, `PlanSystemStart`, `GroupFix`, `WritableFix`, `LinuxWarnings`, `platform.ReadDistro`, `DoctorView.Linux`.
- A read-only config folder: when Visor can't write the folder configs go in (root's, on a Linux package), the dashboard, a config's page and Add new say "Read-only: <folder> belongs to root" with How to allow editing (Doctor), and Save & apply, Remove from supervisor and Restore are off, each saying why. Showing, running, checking and Apply changes still work. `ConfigService.Folder`.
- Ubuntu's AppArmor rule that crashes WebKit's sandbox (`kernel.apparmor_restrict_unprivileged_userns=1` with no profile for Visor) no longer ends in a crash with nothing on screen: Visor stops before its window, prints the AppArmor profile and the `sudo` steps that add it, saves them as `apparmor-fix.txt` in its state folder, and says so in a notification. `platform.WebKitSandboxBlocked`, `platform.AppArmorProfile`.
- Linux packages: `wails3 task linux:package` builds `bin/visor-x86_64.AppImage` (GTK and WebKitGTK inside), `bin/visor.deb` and `bin/visor.rpm`. The packages install `/usr/bin/visor`, `dev.getvisor.visor.desktop` (its `StartupWMClass` matches the window, so the dock and banners show Visor's icon) and the icon at eight hicolor sizes (`go run ./scripts/appicon` now draws `build/linux/icons/` too); they need GTK 4 and WebKitGTK 6.0 and recommend GNOME's AppIndicator extension. The .deb also installs the AppArmor profile `/etc/apparmor.d/dev.getvisor.visor` and loads it, so the window opens on Ubuntu 23.10+. For an AppImage, Visor's own fix covers both ways it runs (its FUSE mount or `--appimage-extract-and-run`). The Arch package and the generated `visor.desktop` are gone.
- The release workflow builds the Linux downloads beside the dmg: `mac`, `linux` and `publish` jobs, with `Visor-<v>-x86_64.AppImage`, `visor_<v>_amd64.deb` and `visor-<v>-1.x86_64.rpm`, each with a `.sha256`, in the draft release. Run by hand (Actions → Release → Run workflow), it is a dry run: everything is built as `0.0.0-dryrun.<n>` and kept as workflow artifacts, with no release.
- `scripts/linux-check.sh build|open`, the Linux counterpart of `sign-check.sh`: builds the AppImage into `/tmp/visor-linuxcheck` and runs it against the sandbox. `scripts/sandbox.sh`'s "supervisord not found" hint names the Linux ways to install it.
- Docs: the README covers Linux (install from the `.deb`, `.rpm` or AppImage, the GNOME tray extension, Ubuntu's AppArmor profile, a supervisord that runs as root, the keyring) and its known limitations; `docs/scripts.md` has a Linux section; `docs/testing.md` has a manual Linux checklist; `docs/beta.md` is the note for beta testers (install, what to try, how to report, where Visor keeps things). The bug report form asks for the operating system, not only the macOS version.
- Fixes from testing on Ubuntu and from review: a config added and applied outside Visor (`supervisorctl update`) no longer stays "changed on disk" once supervisord says nothing differs (Check for changes and Apply changes clear it). Doctor's config-folder fix on Linux uses the socket's group when the config names one, and starts with joining the group (and logging in again) when you aren't in it. An inherited `$APPIMAGE` (Visor started from another AppImage) is ignored unless Visor runs from that AppImage. The AppArmor fix for a copy in `/usr/local/bin` or `/opt` no longer replaces the .deb's own profile. Starting Visor with WebKit's sandbox turned off skips the AppArmor stop. Banner bodies are escaped only for a notification server that reads markup. A locked keyring whose prompt is dismissed is an error again, not "no keyring is running". The distro family comes from the first match in os-release. Doctor's start command and tips no longer mention Homebrew on Linux, and Settings and Issues say "computer" instead of "Mac" there. A session started with the new group as its primary group (`sg`) counts as having it. Visor's "can't open its window" notification no longer stays in the notification list.

### Added
- **Log levels in the Logs tab.** A line that states its level gets a coloured mark (red error, amber warning, blue info, grey debug), and errors and warnings are tinted. Stack-trace lines take the level of the entry above them. Errors, Warnings, Info and Debug filters, with counts, show only those lines. Levels are read from the common formats: Laravel/Monolog, Horizon and `queue:work` (DONE, FAIL, RUNNING), JSON logs (pino, Monolog JSON), `level=` logs (Go slog, logfmt), Python, Rails, Kubernetes klog, nginx, and exception or traceback starts. A log with no levels looks as before.
- **Search the whole log file** (Settings → General, off by default). A log search covers the lines the Logs tab has loaded, and now says so. With the setting on, **Search the whole file** (or Enter) reads the whole file from supervisord, newest first, showing progress, with Stop. It is slower, and on a server it downloads the file over SSH, which the setting's help says.
- **Copy** in the Config tab's bottom bar puts the config's text on the clipboard (your edits, if you have any), on this computer and on servers.
- **Import files** (Add new → Import files): bring in config files you already have, from a repo or written by an assistant. Choose several with Choose files…, or drop them anywhere on Visor's window: dropped files open in Import files from any page. The window takes drops itself (Wails `EnableFileDrop`, `app.FilesDropped` reads them), so a dropped file no longer replaces Visor's page, which WebKitGTK did on Linux. Each file is a card with the name it gets in the include folder (its own, with the extension the include setting loads, so `scheduler.conf` becomes `scheduler.ini` where only `*.ini` is loaded, and it says so), whether it's ready, the problems to fix (each opens its line), and Edit, which opens the same editor and explanation as Write it. The files are checked together: a file name already in the folder, two files with the same name, a program name another file already has or another imported file uses, and anything that isn't text are problems to fix (or untick the file to leave it out). **Add N configs** writes each file and has supervisord add its programs; with "Start them after adding" (on by default) their programs are started too, also the ones with `autostart=false`. The originals are only read. New `ConfigService.CheckImport` and `ConfigService.Import`.
- A config file added outside Visor (copied into the include folder before anyone ran `supervisorctl update`) is now shown as such: the dashboard lists its programs as "Not loaded" with a **Load** button on the file's row, the menu offers "Load into supervisord" and "Load and start all in file" (Stop and Restart are off until it's loaded, with the reason), and the config's page says which programs supervisord hasn't loaded, with Load. Start on such a file loads it first, as `supervisorctl update <group>` would, instead of failing with "There is no process with that name". Load adds only the programs supervisord doesn't know: edits to ones it runs still wait for Apply changes. What is loaded is asked of supervisord at the moment of the action. `ConfigView.NotLoaded`, `ConfigService.LoadFile`.
- Doctor (`#/doctor`, and full-window on first launch): the five setup checks (supervisord installed, config file found, supervisord running, config folder writable, processes found) beside the iridescent lens, whose ring has one segment per check and lights them in order once (no animation with reduced motion), with the fix for the first one that fails: copy-boxes for `brew install supervisor` / `brew services start supervisor`, a config picker with "Where Visor looked" (refused when `VISOR_CONFIG` is set), the three ways out of a root-only socket, `chown` for a config folder you can't write (`mkdir -p` when it doesn't exist yet), and a "Move Visor to Applications first" notice when it runs from the disk image. A wrong username or password, or a saved password the Keychain won't hand over, is its own situation, with Open Settings. When supervisord isn't running, **Start supervisord** starts it as you (never sudo): `brew services start supervisor` for Homebrew's own config with that Homebrew's supervisord (so it also starts after a reboot), otherwise `supervisord -c <config>`; a config with `nodaemon=true` (run by launchd) gets its command to copy instead. If it doesn't start, Doctor shows what supervisord printed, what it wrote to its log file during that start (`[supervisord] logfile=`) and the usual causes. supervisord missing from the login PATH still passes when its server answers. On first launch "Open dashboard" finishes setup with "Open Visor when I log in" and "Notify me when a watched process fails" (both on by default); after setup, a launch whose first connection fails opens Doctor beside the sidebar. Doctor never runs sudo, installs nothing and only checks the config folder with `access(2)`. Headings use Bricolage Grotesque, bundled (`@fontsource-variable/bricolage-grotesque` 5.3.0, OFL). New `internal/doctor` (`Run` over a `Probe`), `DoctorService` (`Run`, `UseConfig`, `Finish`), `SettingsService.FinishSetup`, `platform.DirWritable`.
- Visor's own menu bar (shown while the main window is in front), in place of Wails' default whose View → Reload threw away unsaved edits and whose Help → Learn More loaded wails.io into the window: Visor (About, Preferences… ⌘,, Doctor, Hide, Quit), File (New Config… ⌘N, Close Window), Edit, View (Dashboard ⌘1, Issues ⌘2, Find ⌘F, zoom, full screen), Supervisor (Reload Config ⌘R, Restart All… which asks first), Window and Help (Visor Help and Report an Issue open the browser; Doctor). Choices the page carries out arrive as the `visor:menu` event; Reload Config and Restart All… chosen elsewhere open the dashboard first. `internal/app.BuildAppMenu`.
- Launch at login: Settings → General has a working switch, and so does the menu-bar icon's right-click menu (its check mark follows). Visor writes `~/Library/LaunchAgents/dev.getvisor.visor.plist`, which works for an unsigned app (`platform.LaunchAgent`); `SMAppService` is built in too (`platform.AppService`) for a signed build. It refuses to turn on while Visor runs from the disk image or a quarantine copy ("Move Visor to Applications first"), says when macOS wants an OK in Login Items (with a button to open it), and is unavailable outside the packaged app. A plist left by another copy of Visor (a test build, an older location) reads as off until it's turned on from this one. Turning it on or off from the menu-bar icon updates an open Settings page (`visor:login-item`). New `LoginItemService` (`LaunchAtLogin`, `SetLaunchAtLogin`, `OpenLoginItemsSettings`), `platform.Moved`, `platform.Translocated`.
- Visor's own app icon, the lens from the first-launch screen, in place of the Wails logo (`go run ./scripts/appicon` draws `build/appicon.png` and the Icon Composer layer; `wails3 task common:generate:icons` makes `icons.icns`). The old Wails `Assets.car` is gone until it can be rebuilt with Xcode 26, so macOS uses `icons.icns`.
- README install steps for the unsigned build (Open Anyway on macOS 15+, Control-click → Open on 13–14, or `xattr`; checking the `.sha256`), known limitations, CONTRIBUTING.md, SECURITY.md (private reporting; what Visor can reach), issue forms and a pull request template.
- The menu-bar icon shows the unread notification count beside it, and its right-click menu has "Notifications (N)", which opens the list in the main window. The popover's header (board 9) has the health dot, "N failing" and a bell with the unread count that opens the notifications in the main window. Each config file in the popover shows its Watch switch ("Watching" or "Watch"), so you can see and change which files notify you without opening the main window. The count is sent from launch on, not only when something changes. New `ShellService.OpenNotifications`.
- Settings → Connection: a saved password shows as "Saved in your Keychain" with Change… and Remove password, instead of an empty password box.
- Release workflow (`.github/workflows/release.yml`): a `v*.*.*` tag stamps the version into the app, builds a universal `Visor.app`, packs `Visor-<version>-universal.dmg` with an Applications shortcut (`scripts/release-dmg.sh`) and its `.sha256`, and creates a draft GitHub release that says the build is unsigned. It runs vet, the short Go tests and the frontend checks first; a pre-release tag (`v0.1.0-rc.1`) stamps plain numbers into the bundle (0.1.0) and marks the release as a pre-release; anything but `vX.Y.Z[-suffix]` is refused; the checkout keeps no token in `.git/config`. With the five Apple secrets set it signs with Developer ID and notarizes instead (written, not yet tried).
- Packaging signs with one switch, `SIGN_IDENTITY` in `build/darwin/Taskfile.yml` (default `-`, ad-hoc). `scripts/sign-check.sh` builds a copy signed either way into `/tmp/visor-signcheck` to try what macOS allows it.

- A retry while a program is still starting no longer opens an unexpected exit; FATAL and the crash loop cover programs that can't start.

### Fixed
- A config applied outside Visor (`supervisorctl update`, a deploy script) no longer stays "Changed on disk". Visor only knew what supervisord loaded from its own applies and supervisord restarts, so a file applied another way kept its badge and card. Now, when a file shows as changed, Visor asks supervisord (the re-read `supervisorctl reread` does, which starts and stops nothing) right away, when the Config tab opens, and again every minute while it stays flagged (Settings → Checking and history → **Recheck changed configs every**, 15 to 600 seconds). A file supervisord already runs is recorded as loaded and its badge clears. Servers set to Read only are never asked, and the card says so. The card is titled "Changed on disk since supervisord last loaded it", says when supervisord confirmed the change is still waiting, and on a server offers **Check with supervisord** in place of Apply changes, which configs on servers can't do yet. Check for changes clears every file supervisord already runs, not only when nothing differs.
- Read-only config text (configs on servers, files Visor can't write) selects like any text: a click puts the cursor in the file, Shift+arrows and ⌘A (Ctrl+A) select within it, and ⌘C copies the selection. Before, the file could not take focus, so select-all took the whole page.
- Searching a long log no longer freezes the window. A short query such as one letter froze it for seconds (a highlight per match, tens of thousands of them, redrawn with every new line). Now the newest 1,000 matches are highlighted and the count says when there are more, the search runs once you stop typing, and new lines no longer redraw the lines already shown.
- On macOS, opening Visor while it already ran (from Finder or Spotlight, or another copy started by clicking a notification) crashed the running Visor, and so did a launch by the login item. Both now show the window, or start in the menu bar only.
- Notifications for failures in the first moments after launch were dropped while the permission prompt was still open; a send now waits up to two minutes for the answer.
- A program's history now always shows its stop when it is removed, also when the stop and the removal both happen between two polls ("by you" from Visor, "program removed" from elsewhere).
- A supervisord restart that takes a few seconds (programs slow to stop) no longer opens "supervisord is not responding" or turns the menu-bar icon red: while it stops its programs supervisord still answers (SHUTDOWN_STATE), so those polls don't count as failed. If it then really goes away, the issue opens as before.
- A restart made outside Visor (`supervisorctl restart`, a stop and start from another client, `supervisorctl reload`, SIGHUP, or `supervisorctl update` re-adding a group) no longer opens an unexpected exit or counts toward a crash loop. supervisord logs these as `stopped:`, which Visor now reads (after a daemon restart, from the line before the process's `spawned:` line), and history notes them "Restarted (stopped on request)". The main log is read once per poll however many processes restarted, and a start from STOPPED never counts toward a crash loop.
- Clear logs in a process's menu on the dashboard now asks first, like the Logs tab, and is disabled unless the process is running (supervisord leaves other processes' logs alone and reported success anyway).
- Lowering issue retention no longer deletes history on every spinner click or typo; see Changed.
- Stop all in file and Restart all in file in the dashboard's config menu now ask first, like the config page's buttons.
- Switching Visor to a different supervisord closes the open issues of processes it doesn't run ("not in this supervisord") once it first answers, instead of leaving them open forever.
- Settings: Reconnect is disabled while the connection has unsaved changes ("Save and reconnect to use your changes"), and anything typed while it reconnects is kept.
- "View supervisord log" with no main log file (`logfile=` unset, or syslog) says so and how to fix it, instead of blaming a missing command.
- A lost log stream on the Logs tab explains itself in plain English (for example "supervisord is restarting. Retry in a moment.") instead of showing the raw fault.
- A busy log on the Logs tab no longer re-renders all 5000 lines on every update.
- The config page without a connection to supervisord says why, instead of that the file is not one of supervisord's.
- Start, stop or restart all in a file without a connection to supervisord now says why there is no connection, instead of that the file is unknown.
- Links to a config's page keep its absolute path exactly (it is encoded in the URL).
- A crash that supervisord restarts between two polls now opens an unexpected exit (how Visor tells a crash from a planned exit is under Changed). Every restart is written to the process history.
- Your own start, stop, restart, signal and daemon actions no longer count toward crash loops or open unexpected exits for the restarts they cause, so they no longer turn the tray red; history marks those changes "by you". A program you start that exits with an unexpected code still opens an issue. After you shut supervisord down, no unreachable issue opens until it is back; after you restart it, one opens if it is not back within 30 seconds.
- A dismissed or resolved issue no longer reopens on the next launch when supervisord still shows the same failure; a new failure still opens one.
- A process removed from supervisord closes its open issues ("program removed"), and a process restarted straight into FATAL opens a FATAL issue.
- "Failing for" counts from the latest open FATAL or unexpected exit, not the oldest issue.
- The config watcher stops listing a deleted config file as removed once supervisord restarts.
- Opening Visor brings back a minimised main window.
- A failure in the same second as you dismissed or resolved an earlier one now opens an issue, instead of counting as already dismissed.
- The issue store no longer loses the record written after a line torn by a crash, and a record too large to read is skipped instead of stopping Visor from opening its issue history.
