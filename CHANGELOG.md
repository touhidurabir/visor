# Changelog

All notable changes to this project are documented here.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### A new look
Every screen was redrawn on one set of colours, buttons and type, in light and dark. Buttons still do what they did; the few flow changes are noted below.
- A new app icon, Pulse: a bright ring on dark glass with a mint pulse line. The menu-bar icon is the same ring and pulse, with a hollow badge for a warning and a filled one for an error.
- The dashboard opens with a health strip: one sentence ("2 processes are failing", "All 12 processes are running"), the names of what fails with **Show them**, and small counts, in place of the six tiles. Failing processes come first within their config, on a tinted row with the full reason. Shutting supervisord down now points to Doctor.
- When supervisord isn't running (or wants a password, or won't let Visor in), the dashboard says so in one plain line with **Open Doctor** and **Try again**; the raw error is under Show details. The counts show dashes, the actions that need supervisord are off and say why, and your configs stay listed. When supervisord is there but doesn't answer a check (it timed out, or sent an HTTP error), it says "supervisord isn't answering" and that Visor keeps checking. The sidebar says "Not running" only when supervisord isn't running, "Not answering" for that, and "Not connected" for any other connection problem. A notification for a turned-down password says so ("supervisord wants a password") instead of "Visor can't reach it".
- A config's page has a clearer header (breadcrumb, title, a failing badge, the Watching switch) and a full-height Logs tab with a live dot. Overview opens on "Only problems" when the file has any.
- Issues has one summary line instead of tiles, each kind as an icon and a word, and the whole of what happened with its process and config under it. A crash loop is red there, as it is in the bell and the banners.
- The notification panel (the bell) groups notifications into Today and Earlier, with the severity icon before each title and unread ones in bold.
- macOS banners start with a coloured severity icon (red, orange or blue) before the title, have a one-sentence body that starts with the config file, and stack by config file.
- The menu-bar popover lists failing processes first, in a "Needs attention" group (named `group:name` when the two differ, so two failing `worker`s can be told apart), then each config with its Watch switch; rows show only the actions that apply. When supervisord isn't running it says so plainly, and **Open Doctor** takes the main window straight to Doctor.
- Add new: Write it lists what to fix before saving, each linked to its line, and a save bar stays at the bottom with the status and a Save that says why it waits ("Fix line 4 to save"). The form has its titles inside the cards, a checked template chip and a preview that counts what to check. A config's editor uses the same save bar.
- **Copy an existing config**: Add new → Copy an existing config… opens a copy of any config under new names (`<name>-copy`, then `-copy-2`…), lists what it renamed and warns about values that still name the original and about any log file the copy would share with it (a fixed path, not `AUTO` or one with `%(program_name)s`). The copy's file name stays inside the include pattern (`web-svc.ini` → `web-copy-svc.ini` for `*-svc.ini`). Nothing is written until you save.
- Settings starts with General. Polling, crash loops and issue history share one "Checking and history" card, every row has its label on the left and the control on the right, and Appearance (System, Light, Dark) is only in Settings now, no longer in the sidebar.
- Doctor uses the app's look: a status word beside every check and the fix in one card under the checks.
- "What this config does" is now one card per program instead of one long paragraph. Each card shows the program's name, whether it is running (or "2 of 4 running", or what is failing), what it does in one short sentence, and why it can't run when supervisord says so. Click a card to see its lines; failing programs start open, the others closed, and Expand all / Collapse all open or close them together. The Config tab and Add new use the same cards, with each line written above what it means and the setting's name picked out from its value. "Only problems" never hides a failing program. A Laravel command Visor doesn't know reads as "the Laravel command ocpp:watch-ceilings" instead of "a PHP script".

### Added
- Doctor (`#/doctor`, and full-window on first launch): the five setup checks (supervisord installed, config file found, supervisord running, config folder writable, processes found) beside the iridescent lens, whose ring has one segment per check and lights them in order once (no animation with reduced motion), with the fix for the first one that fails: copy-boxes for `brew install supervisor` / `brew services start supervisor`, a config picker with "Where Visor looked" (refused when `VISOR_CONFIG` is set), the three ways out of a root-only socket, `chown` for a config folder you can't write (`mkdir -p` when it doesn't exist yet), and a "Move Visor to Applications first" notice when it runs from the disk image. A wrong username or password, or a saved password the Keychain won't hand over, is its own situation, with Open Settings. When supervisord isn't running, **Start supervisord** starts it as you (never sudo): `brew services start supervisor` for Homebrew's own config with that Homebrew's supervisord (so it also starts after a reboot), otherwise `supervisord -c <config>`; a config with `nodaemon=true` (run by launchd) gets its command to copy instead. If it doesn't start, Doctor shows what supervisord printed, what it wrote to its log file during that start (`[supervisord] logfile=`) and the usual causes. supervisord missing from the login PATH still passes when its server answers. On first launch "Open dashboard" finishes setup with "Open Visor when I log in" and "Notify me when a watched process fails" (both on by default); after setup, a launch whose first connection fails opens Doctor beside the sidebar. Doctor never runs sudo, installs nothing and only checks the config folder with `access(2)`. Headings use Bricolage Grotesque, bundled (`@fontsource-variable/bricolage-grotesque` 5.3.0, OFL). New `internal/doctor` (`Run` over a `Probe`), `DoctorService` (`Run`, `UseConfig`, `Finish`), `SettingsService.FinishSetup`, `platform.DirWritable`.
- Visor's own menu bar (shown while the main window is in front), in place of Wails' default whose View → Reload threw away unsaved edits and whose Help → Learn More loaded wails.io into the window: Visor (About, Preferences… ⌘,, Doctor, Hide, Quit), File (New Config… ⌘N, Close Window), Edit, View (Dashboard ⌘1, Issues ⌘2, Find ⌘F, zoom, full screen), Supervisor (Reload Config ⌘R, Restart All… which asks first), Window and Help (Visor Help and Report an Issue open the browser; Doctor). Choices the page carries out arrive as the `visor:menu` event; Reload Config and Restart All… chosen elsewhere open the dashboard first. `internal/app.BuildAppMenu`.
- Launch at login: Settings → General has a working switch, and so does the menu-bar icon's right-click menu (its check mark follows). Visor writes `~/Library/LaunchAgents/dev.getvisor.visor.plist`, which works for an unsigned app (`platform.LaunchAgent`); `SMAppService` is built in too (`platform.AppService`) for a signed build. It refuses to turn on while Visor runs from the disk image or a quarantine copy ("Move Visor to Applications first"), says when macOS wants an OK in Login Items (with a button to open it), and is unavailable outside the packaged app. A plist left by another copy of Visor (a test build, an older location) reads as off until it's turned on from this one. Turning it on or off from the menu-bar icon updates an open Settings page (`visor:login-item`). New `LoginItemService` (`LaunchAtLogin`, `SetLaunchAtLogin`, `OpenLoginItemsSettings`), `platform.Moved`, `platform.Translocated`.
- Visor's own app icon, the lens from the first-launch screen, in place of the Wails logo (`go run ./scripts/appicon` draws `build/appicon.png` and the Icon Composer layer; `wails3 task common:generate:icons` makes `icons.icns`). The old Wails `Assets.car` is gone until it can be rebuilt with Xcode 26, so macOS uses `icons.icns`.
- README install steps for the unsigned build (Open Anyway on macOS 15+, Control-click → Open on 13–14, or `xattr`; checking the `.sha256`), known limitations, CONTRIBUTING.md, SECURITY.md (private reporting; what Visor can reach), issue forms and a pull request template.
- The menu-bar icon shows the unread notification count beside it, and its right-click menu has "Notifications (N)", which opens the list in the main window. The popover's header (board 9) has the health dot, "N failing" and a bell with the unread count that opens the notifications in the main window. Each config file in the popover shows its Watch switch ("Watching" or "Watch"), so you can see and change which files notify you without opening the main window. The count is sent from launch on, not only when something changes. New `ShellService.OpenNotifications`.
- Settings → Connection: a saved password shows as "Saved in your Keychain" with Change… and Remove password, instead of an empty password box.
- Release workflow (`.github/workflows/release.yml`): a `v*.*.*` tag stamps the version into the app, builds a universal `Visor.app`, packs `Visor-<version>-universal.dmg` with an Applications shortcut (`scripts/release-dmg.sh`) and its `.sha256`, and creates a draft GitHub release that says the build is unsigned. It runs vet, the short Go tests and the frontend checks first; a pre-release tag (`v0.1.0-rc.1`) stamps plain numbers into the bundle (0.1.0) and marks the release as a pre-release; anything but `vX.Y.Z[-suffix]` is refused; the checkout keeps no token in `.git/config`. With the five Apple secrets set it signs with Developer ID and notarizes instead (written, not yet tried).
- Packaging signs with one switch, `SIGN_IDENTITY` in `build/darwin/Taskfile.yml` (default `-`, ad-hoc). `scripts/sign-check.sh` builds a copy signed either way into `/tmp/visor-signcheck` to try what macOS allows it.
- Notifications you can see in Visor: a bell at the top of the sidebar with the unread count opens a list (Unread / All, "Mark all as read", a link to Settings and to all issues). Every failure the notification settings and watched configs allow lands there, whether or not macOS shows a banner; a notification leads to its config on that process and is then read. When macOS blocks Visor's banners the list says so, with "Allow in System Settings" (`NotifyService.OpenNotificationSettings`); the server build says it can't show banners. supervisord answering again after being unreachable adds a note that is already read. Kept in `notifications.json` in the state folder (newest 200, 30 days). New `notify.Inbox`, `InboxService` (`Notifications`, `MarkRead`, `MarkAllRead`) and the `visor:notifications` event.
- A process that keeps exiting unexpectedly now notifies again: each repeat counts on its open issue (`Issue.Count`, `LastAt`; `Tracker.ApplyAll` returns `Repeated`), updates its unread notification and says "3rd time in 10 minutes" (banners still at most one a minute per process and kind).
- Line-by-line explanation of a config (`describe.Explain`, `ConfigService.Explain`, `ConfigDetailView.Explain`): a plain-English summary, then every line with what it means, the settings a program leaves out with the defaults that apply, and suggested log files when output goes to files supervisord names itself. Problems sit on their line with how to fix them (`validate.Check.Fix`), and some carry the exact change (`validate.Check.Edit`: the `%(process_num)` copy name, a misspelled key, `killasgroup`). The command, folder and log files a line points to are checked on disk (found, missing, size, named by supervisord) with Reveal / Open in Finder, Open in editor, Show in Finder and View in Logs tab. What supervisord says about a failing program shows on the line that causes it and does not block saving.
- Add new (`#/new` and `#/new/form`, ⌘N): create a config two ways that share one draft. "Write it" is a file name (default `<program name>` plus the include pattern's extension, e.g. `.ini`) and the CodeMirror editor, with the checks and the plain-English description updating as you type. "Fill a form" starts from a template (Laravel queue worker, Horizon, scheduler, Node app, any script; paths under /srv/acme and the names are placeholders to change) and has a field for each common setting, each showing the check that applies to it, beside the file that will be written. Switching between them keeps everything: the form re-renders the text, and going back to the form reads the text again (and says when the text has comments or settings the form can't show). "Save & apply" is blocked while there are errors, writes the new file (never over an existing one; a clear message says so), has supervisord add just its programs so the others keep running, turns Watch on for it, and shows a result card with "Open it". New `ConfigService.Create`, `Templates`, `RenderProgram`, `ProgramValues`, `IncludeDir`, `IncludeExt`; `config.Templates`, `config.RenderProgram`, `config.ProgramValues`.
- Apply changes from the dashboard, the file menu, the server menu and the menu-bar popover ("Apply config changes"): Visor first asks supervisord what differs and lists what will be added, restarted or removed in a confirmation, applies it while the buttons stay disabled, and reports the result, with any group that failed listed. Visor flags a file edited on disk at every poll (about a second), so the banner appears without a manual check. "Remove from supervisor" in a file's menu stops its programs and moves the file into Visor's backups folder (Application Support/Visor/backups); a result card with "Undo" brings it back straight away (a failed Undo can be tried again), and "Recently removed" on the dashboard lists removed files that aren't back, with Restore, after the card is gone (`ConfigService.RemovedFiles`). "Apply changes" applies exactly the groups its confirmation listed; a change that turns up meanwhile waits for the next apply and keeps its file flagged. Choosing a template on Add new → Fill a form now asks before replacing text you changed.
- Config tab on a config's page: edit the file in a CodeMirror editor (INI highlighting, light and dark with the app's theme), with checks as you type (errors block saving, a line number jumps to the line), a plain-English description of each program beside it, and "Save & apply": a diff preview of exactly what changes, a backup first, then only this file's programs are applied (changed ones restart, the rest keep running) and a result card lists what was added, restarted or removed. "Restore a backup…" lists every saved version with the change restoring it would make; a restore goes through the same checks and backup, so it can be undone, and brings back a file removed from supervisor. A file edited elsewhere while the editor is open is never overwritten: Visor says so, keeps your edits, and lets you compare, copy them, load the new version or keep yours. A file Visor can't write opens read-only with a pointer to Doctor. Unsaved edits survive switching tabs. When a config changed on disk, the tab shows what differs from what supervisord runs, with "Apply changes". The Overview tab's "What this config does" now shows the description. New `ConfigService` (`Read`, `Validate`, `Describe`, `LoadedDiff`, `Save`, `Backups`, `Restore`, `ApplyFile`). Saves, restores, applies, removals and supervisord restarts run one at a time, from the main window and the menu-bar popover alike. When supervisord refuses a saved or new file (it can't re-read its config), Visor puts the previous version back (or removes the new file), keeps your edits in the editor and shows supervisord's reason, so supervisord is never left unable to restart. Save also applies the programs supervisord loaded from the file when it was changed elsewhere and not applied (a program renamed outside Visor no longer keeps running beside its new name). Visor never reads or writes supervisord.conf itself, even when an include pattern or a symlink reaches it.
- `internal/apply`: safe config writes and `supervisorctl update`. `Write` refuses to overwrite a file edited or deleted elsewhere since it was read (`ErrChangedOnDisk`, by SHA-256) and to replace an existing file when creating one (`ErrExists`); it backs the old content up first, writes a temp file in the same folder, syncs it and renames it into place, keeps the file's mode (new files are 0644) and writes through a symlink instead of replacing it. A folder or file Visor may not write fails with `ErrNotWritable` and leaves no temp file and no backup behind. `Remove` moves a file into the backups (a copy marked removed, then delete). Backups live in the state folder under `backups/<sha1 of the path>/` (0700 folders, 0600 files, `meta.json` names the original path), listed newest first. `Reload` re-reads the config (`reloadConfig`) and applies removed groups (stop, waiting until stopped, then remove), changed groups (the same, then add) and added groups, optionally only some groups, reporting per-group failures.
- `ServerService.ApplyChanges(groups)` (every change when `groups` is null) and `ServerService.RemoveFromSupervisor(path)` (back the file up, stop the file's processes, move the file into Visor's backups, remove its groups; nothing is stopped if the folder can't be written or the backup can't be saved). Applied files are recorded as what supervisord runs, so their "changed" flag clears, including comment-only edits and files deleted outside Visor; a group that fails keeps its file flagged. Removing a program opens no issue and sends no notification; its open issues close as "program removed" (a changed program that is stopped and added again closes them as "config applied"). Saving a config restarts its programs as your action too: no notification, no unexpected-exit issue, history says "by you".
- `internal/describe`: explains each `[program:x]` in plain English from its keys and supervisord's defaults (command, folder, user, start behaviour, copies, restart policy, stop grace, where output and errors go), with "worth a look" flags: `autorestart=true` with `startsecs` of 1 or less, running as root, no `stderr_logfile` while `redirect_stderr` is off, a log with `maxbytes=0`, and `numprocs>1` without `%(process_num)`. No AI; golden-file tested.
- `internal/validate`: checks a program config before it is saved (file name matches the include setting, parse errors with their line, name unique across all configs, unknown keys with "Did you mean", values checked exactly as supervisord 4.2.5 parses them (whole numbers including negative ones, sizes, true/false words such as yes/on/1, `autorestart`, any signal name or number for `stopsignal`, `exitcodes`, `umask`, and `environment` with supervisord's own quoting rules, warning when it would silently cut a value short), names without spaces, colons or slashes, `stopasgroup` needs `killasgroup`, `numprocs>1` needs `%(process_num)`, a `user` that exists (supervisord refuses others), no `[supervisord]`, `[unix_http_server]`, `[inet_http_server]`, `[supervisorctl]`, `[include]` or `[rpcinterface:x]` section in an include file, command found on your login-shell PATH, `directory`, log folders writable). `describe` reads `autorestart=yes` (and other true/false words) as supervisord does. The form keeps a multi-line `environment=` intact. Errors block saving; warnings don't. `internal/platform.LoginPATH` reads `$SHELL -l -c 'printf %s "$PATH"'` once (2 s timeout, cached) and adds the Homebrew folders; `platform.LookPath` searches a given path.
- Native macOS notifications: each new issue in a watched config (a process can't start, exits unexpectedly or keeps restarting) and supervisord not responding shows a notification straight away, e.g. "mailer-digest can't start" with the reason and config file. The Settings switches (master and per kind) and each config's Watch toggle decide which; repeats for the same process and kind are held back for a minute (a notification macOS did not show does not count). Clicking one opens Issues, and a notified issue shows the bell. Visor asks for permission on first launch; Settings → Notifications shows whether macOS allows them ("Not allowed. Allow Visor in System Settings → Notifications." until you allow them) and has a "Send a test notification" button. Quitting waits at most 2 seconds for notifications still being sent. Notifications need the packaged `Visor.app`: in `task dev` and other bare binaries (no bundle identifier) and in the server build they are off and the app runs on. New `internal/notify` (which issues notify, wording, rate limit), `Tracker.MarkNotified`, `RuntimeOptions.Notifier`, and `NotifyService` (`NotificationStatus`, `SendTestNotification`). Sending never holds up the poll loop.
- Appearance: choose System, Light or Dark with a three-icon switch in the sidebar footer or in Settings → General (arrow keys move between options). System follows macOS live; the choice applies before the first paint (no flash), reaches the menu-bar popover at once, and also sets the native window chrome (title bar, scroll bars) on macOS. Saved as `appearance` in `settings.json` through the new `SettingsService.SetAppearance`, one change at a time, so quick switching or a Settings save at the same moment never stores an older choice (`Save` leaves the appearance alone); a new `visor:settings` event carries each save to every window. Dark tokens now live under `data-theme="dark"` instead of a media query.
- Action menus (the ⋯ buttons) redesigned: each item has an icon, its label on one line and the whole matching `supervisorctl` command below it in grey (long commands wrap instead of being cut), a copy button for the command (or ⌘C on the focused item; "Copied" shows only when the text really reached the clipboard, and in a browser the page's own clipboard is used), and a fixed 360 px width. The menu flips upward or leftward near the window edge. Commands use the shortest name supervisorctl accepts (`mailer-digest`, not `mailer-digest:mailer-digest`; numbered or grouped processes keep `group:name`).
- Settings fills the window instead of stopping at 760 px; from 1100 px wide the cards sit in two aligned columns with Connection across the top.

- Playwright UI tests (`wails3 task test:e2e`, `e2e/`): the real frontend in WebKit through the Wails server-mode build (`go build -tags server`), against a throwaway supervisord in `/tmp/visor-e2e`; smoke specs for the dashboard, process actions, config detail, issues, settings and navigation, run in CI on Ubuntu. `scripts/sandbox.sh` takes `VISOR_SANDBOX_DIR` (must be `/tmp/visor-<name>`) and works with Linux `ps`; the server build keeps saved passwords in memory (`settings.MemoryKeychain`) and never uses the login Keychain. See `docs/testing.md`.
- Settings page (`#/settings`): Connection (config file with Choose… and Use auto-detect, the socket it names, username and password, Save and reconnect or Reconnect, connection status), polling interval (1–10 s), notifications (master switch plus FATAL, unexpected exit, crash loop and unreachable), crash-loop thresholds (restarts within minutes), issue retention (at least 7 days), Launch at login (coming in this release) and appearance. Everything but the connection and retention saves as it changes; out-of-range values are clamped and the page says what it kept. With `VISOR_CONFIG` set, the config file is shown as "Set by VISOR_CONFIG" and can't be changed.
- `internal/settings`: `settings.json` in the state folder (atomic write, 0600; a missing key keeps its default; values clamped on load and save) and the supervisord password in the macOS Keychain (service `dev.getvisor.visor`, account = config path) via `github.com/zalando/go-keyring` v0.2.8. A username saved in Settings, with its Keychain password, overrides the config's `[supervisorctl]` credentials. The password follows the config when the config file changes; removing it (or clearing the username) goes back to the config's credentials. Overlapping changes on the Settings page are saved one after another, so none is lost.
- `SettingsService` (`Get`, `Save`, `SaveConnection`, `ApplyRetention`, `ChooseConfig`) and `ServerService.Reconnect`, which rebuilds the connection with the current settings and returns the overview after its first poll (for Doctor's "Check again").
- supervisord log tab (`#/issues/log`): supervisord's own log parsed into lines with time, level pill (CRIT/ERRO, WARN, INFO, DEBG/TRAC/BLAT) and text, with traceback lines kept under their entry. Filter by level chip (Debug off by default), date (presets or custom range) and search; Refresh, or Follow to add new lines every 2 seconds while the tab and window are visible. Follow reads only what was written since its last read (the newest 64 KiB, falling back to a full read after a rotation or a burst), and waits for one read to finish before the next. Filters live in the URL. A full read takes the newest 4 MiB and shows up to 2000 matching lines, and says when older log was not read. `ServerService.MainLogLines` (with an `After` cursor for following), `supervisor.Client.ReadMainLog` and `supervisor.ParseMainLogLines` replace `ServerService.MainLog`; the dashboard's "View supervisord log" item opens the tab instead of a dialog.
- Issues page: a stats strip (total, open, resolved, last 24 hours, 7 days and 30 days), filters by status, kind, date (presets or a custom range) and "Notified only", search, multi-select with Resolve N and Delete N (both ask first; only Delete uses the red button), a Delete button on resolved rows, and paging back through history 50 at a time; each issue shows how long it lasted and a bell when it notified you. Filters live in the URL, and each tab keeps its own when you switch between them. The page has two tabs, Issues and supervisord log (`#/issues/log`). `IssueService` gains `Stats`, `ResolveMany` and `Delete`, and `List` takes an `IssueQuery` (status, kind, notified, date range, cursor, search); `Counts` is gone. Deleting removes only resolved or dismissed issues and leaves the history alone; resolving in bulk, like resolving one, keeps Visor from reopening the same failure, and so does deleting a resolved issue, even after Visor relaunches (the store keeps a small `suppressed.jsonl` record, pruned with the retention window). The table fits a 1280 px window without cutting off the row buttons.
- `internal/logs`: overlap-safe log tailer. Each poll returns only new output (first poll: last 64 KiB), detects a cleared or rotated log (`Truncated`) and output lost to overflow (`Skipped`), keeps the newest 1 MiB in a line-aligned buffer (or nothing, with `NoBuffer`, which the Logs tab's followers use), and reports a stream with no log file as `ErrNoLog`.
- Main window shell: sidebar (Local health and failing count, Dashboard, Issues badge, Add new, Doctor, Settings), design tokens with a dark palette, vue-router (hash history; `#/tray` stays outside the shell), and keyboard-accessible action menus with confirmation for destructive items.
- The menu-bar popover is now a non-activating floating panel that joins all Spaces and can show over full-screen apps.
- Wails v3.0.0 app scaffold (Vue 3 + TypeScript frontend), bundle ID `dev.getvisor.visor`, minimum macOS 13.
- `internal/supervisor/xmlrpc`: dependency-free XML-RPC codec for supervisord. Log tails containing ANSI colour codes, other control characters, `\r` or invalid UTF-8 decode byte-for-byte instead of failing.
- `internal/supervisor`: typed client for every supervisord RPC Visor needs (status, start/stop/restart, groups, signals, log tails, reloadConfig/add/remove, restart/shutdown) over a pluggable `Transport` (unix socket and TCP), with basic auth, per-call timeouts, and faults matchable via `errors.Is` (`ErrNotRunning`, `ErrBadName`, …, plus `ErrUnreachable` and `ErrUnauthorized`).
- `internal/supervisor/supervisortest`: test harness that runs a real supervisord in a temp dir with dummy programs, and always shuts it down (killing stuck programs) even when a test fails or panics. Integration tests cover process control, groups, signals, log tails, `reloadConfig` add/remove, and daemon restart.
- `internal/config`: read-only parser for supervisord.conf (continuation lines, `;` inline comments only after whitespace, `%(here)s` and `%(name)02d` expansion) and config discovery that finds the socket or port, credentials, include globs and pidfile. The live check now finds the socket this way.
- `internal/app` `ServerService` lists processes to the frontend (first window shows name, group and state, or an error panel). `scripts/sandbox.sh up|down|status` runs a throwaway supervisord under `/tmp/visor-sandbox` with 12 sample processes, and `task dev` now always runs against it, so development never touches the real supervisord.
- GitHub Actions CI on macOS: `go vet`, golangci-lint, `go test -race` (with a real supervisord), a check that core `internal/` packages never import Wails (`scripts/check-core-imports.sh`), and frontend typecheck, tests and build. All actions are pinned by commit SHA.
- `internal/monitor`: one poll loop (default every 2s, `Poke` to poll now) that snapshots supervisord, diffs snapshots into events (state changed, added, removed, restarted between polls, unreachable once per outage, reconnected; the first contact after starting unreachable is not a reconnect) and computes aggregate health (error on FATAL, an unexpected EXITED status or an unreachable daemon; warning on STARTING, BACKOFF or STOPPING). Subscribers never block the loop: one that falls behind gets the latest snapshot with the events it missed merged in. Survives supervisord restarts.
- `internal/issues`: turns monitor updates into issues and history. Opens FATAL, unexpected exit (including restarts between polls), crash loop (5 restarts in 10 minutes) and unreachable issues with no duplicates; FATAL and unreachable close themselves, crash loops wait for you. Stores issues and every state change as append-only JSONL (private, compacted after 90 days).
- `internal/config`: include-file inventory (programs, `[group:x]` membership, `numprocs`, `exitcodes`) and an on-disk change watcher that reports files changed, added, removed or uncertain relative to what supervisord last loaded, without calling supervisord.
- Live overview: `internal/app` now runs the monitor, issue tracker and config watcher for the app's lifetime and pushes a `visor:overview` event (server health, version, uptime, stats, configs with their processes, "up / failing / stopped for" labels, open issues) after every poll and action, plus `visor:issue-opened`. `ServerService` gains process, group, per-file and all-process start/stop/restart, signals, clear logs, check for changes, restart and shut down supervisord, and the supervisord log; `IssueService` lists, resolves and dismisses issues and returns process history. Per-config Watch toggles persist in `watch.json`. State lives in `~/Library/Application Support/Visor` (override with `VISOR_STATE_DIR`; `task dev` uses `/tmp/visor-sandbox/state`). The first window now shows configs with their processes and updates live.

### Changed
- A chosen config file must look like a supervisord.conf (one of `[supervisord]`, `[unix_http_server]`, `[inet_http_server]`, `[supervisorctl]` or `[include]`); any other file is refused with the reason (`config.ErrNotSupervisord`), in Settings and in Doctor.
- Settings saves never change whether first-run setup is done.
- A config's Overview tab: the last error card stays on top and now says which line causes the failure ("Caused by line 8"), then "What this config does" and "Line by line". The separate paths card is gone: each path sits on the line that sets it. "Edit line N" and "Apply fix in the editor" open the Config tab on that line with the change made but not saved. Links can open the Logs tab on a stream (`?stream=stderr`) and the editor on a line (`?line=9`).
- Add new → Write it shows the summary above, the editor beside "Line by line", fixes that apply to the text ("Apply fix", "Add both lines"), and the save button says what is left ("Fix 1 line to save"). Fill a form and the Config tab show the same explanation in place of the Validation and description cards.
- Select fields are drawn like the text fields beside them (same height, border and padding, with Visor's own chevron); WebKit's native pop-up button ignored their size.
- The supervisord log tab is easier to read: roomier rows, 13 px text, wider time and level columns, and a hover highlight.
- The dashboard no longer lists unresolved issues: the Open issues tile links to the Issues page, which has them all. `OverviewView.Issues` is gone (the overview keeps the open-issue count).
- The dashboard table fits the default 1000 px window: below about 990 px of table width the Details column is hidden, so the process names and the ⋯ menus stay in view without scrolling sideways.
- CI runs on pull requests (every push to the PR branch) and on pushes to `main`, not on every branch push.
- The connection to supervisord is rebuilt, not cached forever: Reconnect, or changing the config path or credentials, stops the monitor and its goroutines, closes the client's idle connections, re-discovers the config and starts fresh. A startup config or connection error no longer leaves the app dead until it restarts. Issue tracking (actions in progress, a shutdown you asked for, crash-loop counts) carries across a reconnect, and an action cut short by one says "Reconnecting to supervisord… try again." Followed logs end with "Stopped following because Visor reconnected…" and offer Retry.
- Poll interval (`Monitor.SetInterval`) and crash-loop thresholds (`Tracker.SetRules`) now come from Settings and apply without reconnecting. Issue retention is edited as a draft with Apply: a longer time saves straight away, and a shorter one first asks "Delete issues and history older than N days?" and deletes only once you choose Delete older issues (`SettingsService.ApplyRetention`; the settings auto-save never changes retention or deletes anything).
- Issues page: the retention note shows the setting, and a failure to load the counts no longer blanks the list.
- Config menu hints name the file's real groups (`start mail:*`), not the file name.
- The popover's config button is now "Check for changes", and its notice says nothing was applied yet.
- An open unexpected exit raises the tray to a warning (the process may be running again); a crash loop stays an error.
- An unreachable supervisord turns the tray icon red from the second failed poll in a row (when its issue opens); a single failed poll shows a warning.
- `IssueService.List` takes a `beforeID` after `beforeMs`: "Load older" pages on (opened time, ID), so issues opened in the same millisecond are neither skipped nor repeated. Issues carry a `Note` saying why Visor closed them.
- README: develop with `wails3 task dev` (sandbox supervisord); bare `wails3 dev` talks to the real one.
- When supervisord restarts a process between two polls, Visor reads why it exited from supervisord's main log (`supervisor.readLog`, new `Client.RecentProcessLog`, `ParseProcessLog` and `ParseExitLines`). A planned exit (e.g. `queue:work --max-time` exiting 0) opens nothing, and a crash opens an unexpected exit under every `autorestart` setting, saying how it ended: "Exited with status 1 and was restarted by supervisord" or "Was terminated by SIGSEGV and restarted by supervisord". When the log can't tell (no `logfile`, logging to syslog, or two groups with the same process name), the restart opens "Exited and was restarted by supervisord" under `autorestart=unexpected` (the default) and only counts toward a crash loop under `autorestart=true`.
- A retry while a program is still starting no longer opens an unexpected exit; FATAL and the crash loop cover programs that can't start.

### Fixed
- Notifications for failures in the first moments after launch were dropped while the permission prompt was still open; a send now waits up to two minutes for the answer.
- A program's history now always shows its stop when it is removed, also when the stop and the removal both happen between two polls ("by you" from Visor, "program removed" from elsewhere).
- A supervisord restart that takes a few seconds (programs slow to stop) no longer opens "supervisord is not responding" or turns the menu-bar icon red: while it stops its programs supervisord still answers (SHUTDOWN_STATE), so those polls don't count as failed. If it then really goes away, the issue opens as before.
- A restart made outside Visor (`supervisorctl restart`, a stop and start from another client, `supervisorctl reload`, SIGHUP, or `supervisorctl update` re-adding a group) no longer opens an unexpected exit or counts toward a crash loop. supervisord logs these as `stopped:`, which Visor now reads (after a daemon restart, from the line before the process's `spawned:` line), and history notes them "Restarted (stopped on request)". The main log is read once per poll however many processes restarted, and a start from STOPPED never counts toward a crash loop.
- Clear logs in a process's menu on the dashboard now asks first, like the Logs tab, and is disabled unless the process is running (supervisord leaves other processes' logs alone and reported success anyway).
- Lowering issue retention no longer deletes history on every spinner click or typo; see Changed.
- Stop all in file and Restart all in file in the dashboard's config menu now ask first, like the config page's buttons.
- Switching Visor to a different supervisord closes the open issues of processes it doesn't run ("not in this supervisord") once it first answers, instead of leaving them open forever.
- Settings: Reconnect is disabled while the connection has unsaved changes ("Save and reconnect to use your changes"), and anything typed while it reconnects is kept.
- "View supervisord log" with no main log file (`logfile=` unset, or syslog) says so and how to fix it, instead of blaming a missing command.
- A lost log stream on the Logs tab explains itself in plain English (for example "supervisord is restarting. Retry in a moment.") instead of showing the raw fault.
- A busy log on the Logs tab no longer re-renders all 5000 lines on every update.
- The config page without a connection to supervisord says why, instead of that the file is not one of supervisord's.
- Start, stop or restart all in a file without a connection to supervisord now says why there is no connection, instead of that the file is unknown.
- Links to a config's page keep its absolute path exactly (it is encoded in the URL).
- A crash that supervisord restarts between two polls now opens an unexpected exit (how Visor tells a crash from a planned exit is under Changed). Every restart is written to the process history.
- Your own start, stop, restart, signal and daemon actions no longer count toward crash loops or open unexpected exits for the restarts they cause, so they no longer turn the tray red; history marks those changes "by you". A program you start that exits with an unexpected code still opens an issue. After you shut supervisord down, no unreachable issue opens until it is back; after you restart it, one opens if it is not back within 30 seconds.
- A dismissed or resolved issue no longer reopens on the next launch when supervisord still shows the same failure; a new failure still opens one.
- A process removed from supervisord closes its open issues ("program removed"), and a process restarted straight into FATAL opens a FATAL issue.
- "Failing for" counts from the latest open FATAL or unexpected exit, not the oldest issue.
- The config watcher stops listing a deleted config file as removed once supervisord restarts.
- Opening Visor brings back a minimised main window.
- A failure in the same second as you dismissed or resolved an earlier one now opens an issue, instead of counting as already dismissed.
- The issue store no longer loses the record written after a line torn by a crash, and a record too large to read is skipped instead of stopping Visor from opening its issue history.
